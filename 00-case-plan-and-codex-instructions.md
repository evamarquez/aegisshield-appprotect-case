# Case 02 - Plan and step-by-step instructions

## Result

Create a fictional product case for AegisShield AppProtect. The final case will include management documents, a visual prototype, simple diagrams, simulated execution evidence, and a printable document pack.

## Important rules

- Keep this case separate from Case 01 - Cybersecurity Platform Modernization.
- Do not change the Case 01 PDF while building this case.
- Clearly label fictional customers, interviews, findings, costs, dates, and outcomes as simulated.
- Do not call a prototype a working security product.
- Do not assume that a delay must happen. A change request is recorded only if the fictional execution creates a reason for one.
- Use short, clear language and add a small vocabulary section to each document.
- Review each part before moving to the next one.

## Prompt format for each step

Every implementation prompt should include:

1. Objective - what this step is meant to decide or create.
2. Context - the facts and boundaries already approved.
3. Approved content - the exact information that must appear.
4. Deliverable - the file, page, prototype, or evidence to create.
5. Check - how we know the step is complete.

## Stages

### 1. Define the initiative

Create the Sponsor Handoff and Scenario. Explain the product idea, the customer problem, the possible pilot, the relationship to the SIEM, the sponsor request, and the discovery boundaries.

### 2. Justify the product

Create the Product Discovery and Business Case. Compare competitors and alternatives, including continue, buy, resell, integrate, or build. Treat the value proposition, interviews, and findings as hypotheses until they are tested.

### 3. Record the discovery decision

Create Discovery Findings and Sponsor Decision. Record the simulated customer findings, options considered, recommendation, sponsor decision, approved boundary, and conditions for the next stage.

### 4. Define the first version

Create the Project Brief, Project Charter, product scope, roles, permissions, acceptance criteria, and the engineering investigation of an existing security engine.

### 5. Design the experience

Create the administrator journey and prototype screens. Show setup, rule configuration, event review, a blocked request, and correction of a rule that affected a legitimate booking. Use simulated data and state clearly that the prototype is not functional protection.

### 6. Plan the delivery

Create stakeholders, communication plan, kickoff, requirements, technical approach, WBS tree, RACI, backlog, estimates, budget, Gantt, and team capacity. Calculate the schedule from scope and proposed resources.

### 7. Plan tests and risks

Define tests for malicious requests, legitimate bookings, performance, permissions, data protection, monitoring, and recovery. Record risks such as false positives, service interruption, performance limits, and sensitive data in logs.

### 8. Represent execution

Create the execution board after the case is defined. Use real tool records only when they are ready, and label screenshots as simulated project evidence. If the fictional rule blocks a legitimate booking, record investigation, options, and the selected response. Add a change request only if the scenario supports one.

### 9. Validate, close, and publish

Prepare test results, BookEasy acceptance, launch decision, execution record, stabilization, operations handover, closure, lessons learned, and the portfolio page. Include the prototype, diagrams, screenshots, and printable documents.
